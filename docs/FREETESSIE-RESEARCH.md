Verbatim verified fact list compiled for the backseat-tesla "free Tessie" design brief.

## tessie-surface

Tessie is a thin, metered-cost-absorbing layer on top of Tesla's own official Fleet API/Fleet Telemetry: one static bearer token drives VIN-scoped REST endpoints for reading vehicle state/history and sending commands, plus Tessie-hosted infra (telemetry receiver, geocoding, map tiles, wake/retry logic) that a self-hosted clone would have to replicate or substitute. There is NO permanent free tier (only a trial); paid plans run $6.99-$19.99/vehicle/month and explicitly include "Tesla fees." The economic trick a free clone must copy: use Tesla's push-based Fleet Telemetry (cheap, ~$0.0001/signal) instead of polling vehicle_data (~$0.002/request, which Tessie's own marketing shows balloons to $1,036/vehicle/month at 5s polling) — Tesla gives each developer a $10/month free credit that likely covers a hobby self-hosted setup on telemetry alone, but commands ($0.001 ea) and wake-ups ($0.02 ea, the priciest unit) still meter against that credit. Endpoint surface is large and mostly 1:1 mappable onto Tesla's own Fleet API (state/battery/location/drives/charges/idles/tire-pressure/commands), with Tessie-added value-add endpoints (battery-health trends, driving path, drive/charge tagging, charging invoices, map image, consumption, weather, release notes) and account features (drivers/invitations/roles) that have no Fleet API equivalent and would need to be built from scratch, stored in a self-hosted DB. Automations/alerts/sharing/geofencing appear to be Tessie-app-only features (configured in-app), not exposed as discrete REST endpoints in the public API reference — this should be re-verified before treating it as a spec requirement.

## fleet-auth

Tesla's official Fleet API can replace Tessie's paid middleman layer, but 'fully free' needs an asterisk: app creation needs a Tesla developer account (verified email + MFA, legal business/app details) and no upfront card, yet Fleet API itself is billed pay-per-use (status<500 = billable) with a $10/month per-account discount that comfortably covers 1-2 personal vehicles if telemetry streaming (not vehicle_data polling) is used — so it's 'free' in the sense of no subscription to a third party, not literally zero-cost to Tesla. Technically: host a secp256r1 PEM public key at the fixed well-known path on your own domain, register it with POST /api/1/partner_accounts using a partner (client_credentials) token minted at fleet-auth.prd.vn.cloud.tesla.com (NOT the old auth.tesla.com — that token-exchange host moved in July/Aug 2025), then run a standard (non-PKCE) OAuth authorization-code flow for the end user at auth.tesla.com/oauth2/v3/authorize with scopes like vehicle_device_data/vehicle_cmds/vehicle_charging_cmds/vehicle_location, storing the refresh_token (valid up to ~3 months idle). Regional Fleet API hosts are fixed (NA/AP, EU/ME/Africa, China) and passed as the 'audience' at token time. The one unavoidable manual step is virtual-key pairing: opening https://tesla.com/_ak/<your-domain> from the Tesla phone app on a device with vehicle access — Tesla cannot remotely add the key to a normally-purchased car. No Autopilot/FSD/Summon scopes were touched or needed.

## fleet-commands

Fleet API facts, sourced primarily from Tesla's own developer.tesla.com pages and the authoritative teslamotors/vehicle-command Go source (which is the literal REST-to-signed-command mapping, since the HTML docs page doesn't render parameter/body tables through automated fetch). vehicle_data (GET /api/1/vehicles/{vin}/vehicle_data) and wake_up (POST .../wake_up, 10-60s per Tesla's own best-practices page) are confirmed; exact command body field names for set_temps, set_charge_limit, actuate_trunk, set_sentry_mode, window_control, and set_scheduled_departure were extracted directly from pkg/proxy/command.go. Key finding: navigation_request ("share" a destination) is explicitly excluded from the signed protocol in Tesla's own source (ErrCommandUseRESTAPI) and must go through plain REST even on signed-required cars. Signing is required on everything except pre-2021 Model S/X; an unsigned call on a signed-required car returns a documented 403 with a specific error body. No maintained npm package implements the signing protocol natively — @teslemetry/api and friends wrap Teslemetry's paid hosted relay. One real, license-clean (MIT) native TypeScript/WebCrypto proof-of-concept exists (Oceanswave/tesla-mcp) but only implements the lock command as an "owner-only MVP," leaving the rest of the protocol unported. Recommendation evidence points toward running Tesla's own tesla-http-proxy Go binary as a local sidecar (one binary, a TLS cert/key pair, same REST paths) rather than reimplementing signing natively in TS — the existing VehicleAdapter interface in this repo would plug into it almost the same way TessieAdapter plugs into Tessie today.

## fleet-billing

Tesla's Fleet API bills per call: vehicle_data read $0.002, command $0.001, wake $0.02, Fleet-Telemetry streamed signal $0.0001 (only on change). Every account gets a flat $10/month credit; default billing limit is $0 and apps auto-disable without a payment method or over their limit. Rate limits (per device, per account): 60/min realtime data, 30/min commands, 3/min wakes. For one car: (a) an on-demand texting agent (20 reads+10 commands+3 wakes/day) costs ~$3.30/mo, inside the credit, $0 net. (b) a naive Tessie clone polling vehicle_data every 60s for 8h/day awake (480 reads/day) costs ~$28.80/mo, blowing the credit by ~$19/mo net — this is exactly the behavior Tesla's pricing taxes (Teslemetry says their legacy 20s-polling architecture would cost them >$1M/yr at fleet scale). (c) the same 8h/day logged via Fleet Telemetry streaming instead, using Tesla's own worked example (~15 signals/min driving, $0.00636/hr), costs ~$1.53/mo — inside the credit, $0 net. Conclusion: a free single-car "Tessie" is achievable only by avoiding timed vehicle_data polling — build the texting agent on on-demand reads/commands and any always-on logging/dashboard on Fleet Telemetry streaming, not a 60-second poll loop. Fleet Telemetry itself requires a public FQDN, a TLS/mTLS cert terminated by the telemetry service itself, an open port for the vehicle's WebSocket, and a per-vehicle virtual-key pairing (confirmed by the API's own missing_key error) before fleet_telemetry_config will accept a push. Tesla's/GitHub's docs describe production infra (firewall/LB → Fleet Telemetry → Kafka) and never mention or endorse a home-Mac-behind-a-tunnel deployment; a cheap cloud VM with a real domain + Let's Encrypt cert is the documented, low-friction path instead.

## free-hosting

Tesla's Fleet API requires an HTTPS domain serving a PEM public key at the fixed path /.well-known/appspecific/com.tesla.3p.public-key.pem (no redirects, CA Tesla trusts), plus a separate OAuth "Allowed Redirect URI" that can live on an entirely different host. Real developer reports confirm free platform subdomains CAN be the registered domain itself: multiple live repos serve the key straight from <user>.github.io (needs an empty .nojekyll — Jekyll otherwise drops .well-known/). Cloudflare Pages has the same dot-folder problem, fixed with .assetsignore + "!.well-known". No confirmed report either way exists for bare vercel.app/pages.dev/workers.dev as the registered domain itself. Tesla's validator separately rejects on CA-allowlist/content-type mismatches unrelated to hosting choice, and forbids serving the key via redirect. Recommended $0 stack: host only the key on GitHub Pages (never sleeps, free, proven) while the actual Node+SQLite bot runs on Render's free tier (750 free hrs/month ≈ a full month, 15-min sleep/~1-min wake, kept awake with a free external pinger), with the OAuth redirect_uri pointed at Render's own host — splitting is allowed because Tesla validates Allowed Origin and Allowed Redirect URI independently. Recommended ~$10/yr stack: buy one domain at Cloudflare Registrar (at-cost, $10.46/yr, no renewal hike), run a named `cloudflared` tunnel on Angus's always-on Mac, and serve everything — key, OAuth callback, bot — from one process, avoiding split-hosting and cold starts; this pattern (Cloudflare Tunnel + custom domain) is directly validated by a real Home Assistant user's working setup. Fly.io's free tier is gone (min $2.19/mo, card required); Oracle's Always-Free ARM tier was halved in 2026 with frequent provisioning failures, so it's not a reliable $0 pick right now; eu.org-style free domains work technically but carry an abuse-pattern reputation that cuts against Tesla's own anti-abuse domain checks.

## oss-landscape

Researched existing free/open-source Tessie alternatives on Tesla's official Fleet API. Core finding: the Fleet API mandates signed commands on vehicles from ~2023+, and essentially every tool in this space (Home Assistant's Tesla Fleet integration, community HTTP-proxy add-ons, the TypeScript SDK `tesdk`) handles signing the same way — by running Tesla's own open-source Go binary (`teslamotors/vehicle-command`, Apache 2.0) as a local proxy/sidecar, not by reimplementing the crypto. The one exception is Python's `python-tesla-fleet-api` (Teslemetry's lib, Apache 2.0), which signs natively in Python — a candidate reference for porting to TS, though its exact crypto primitives weren't confirmed in docs. TeslaMate (AGPL-3.0, very active, Elixir+Postgres+Grafana) has already migrated its command path to the Fleet API and documents the same developer-app + proxy + Fleet Telemetry setup we'd need; its AGPL license means copy-as-reference only, not literal reuse. Teslemetry and MyTeslaMate are both paid hosted layers (not free, not useful as code) — Teslemetry ~€3.17/device/month, MyTeslaMate pay-as-you-go with no free tier. TeslaPy (MIT) is dead-end legacy: it explicitly doesn't support signed commands and only works on pre-2021 Model S/X. Tesla's own pricing (per Teslemetry's blog, citing Tesla's rates) gives a $10/month free credit, with commands at $0.001/request, data at $0.002, wake at $0.02, streaming at $0.0001/signal — meaning polling-heavy designs burn the free tier fast, but streaming-first designs stay free indefinitely. The existing repo's `fleetApiAdapter.ts` stub is correctly targeting signed commands; it just needs a key-pair + public-key-hosting setup (confirmed exact path: `/.well-known/appspecific/com.tesla.3p.public-key.pem` on a stable domain) and a running vehicle-command proxy to fill in. Gap: no project reviewed exposes a drop-in Tessie-shaped REST surface (the `{vin}/state`, `{vin}/command/{name}` contract our `VehicleAdapter` already expects) on top of the free Fleet API — TeslaMate is a data logger with its own schema, Home Assistant ties everything to its entity model, and the Fleet-API client libraries (tesdk, python-tesla-fleet-api) are building blocks, not finished Tessie-compatible services. ## portal-practicalities

Tesla's Fleet API is the real "free Tessie" path: one developer app, with each vehicle owner granting OAuth consent individually, is Tesla's own documented and sanctioned architecture (it's exactly how Tessie/Teslemetry work) — so for Angus's own single car there's no "one app per owner" problem. App approval is now largely automatic (minutes-hours, not the old 5-business-day SLA). A $10/month per-account credit is free and needs no credit card up front, but the default billing limit is $0, so any usage above that free credit requires a payment method or the app gets auto-disabled; apps unpaid for 30+ days can be disabled outright, and exceeding the limit permanently drops Fleet Telemetry configs (not auto-restored). The ten gotchas most likely to bite a first-time builder: (1) virtual-key pairing needs the car online + Tesla app ≥4.27.3; (2) changing the Tesla password instantly kills all OAuth tokens with no workaround — must redo /authorize; (3) refresh tokens rotate and die after 3 months (24h grace on the prior one); (4) old unsigned REST commands are deprecated — only the signed Vehicle Command Protocol works; (5) a billed command can still fail if the key silently un-paired — check fleet_status first; (6) NA/EU/China are separate API bases needing separate partner_accounts registration, China needs a wholly separate account; (7) vehicle_location became its own scope (Jan 2025) — old consents don't cover it; (8) the OAuth token endpoint moved (auth.tesla.com → fleet-auth.prd.vn.cloud.tesla.com), old tutorials break with "unexpected issuer"; (9) app registration needs a real HTTPS domain hosting a public-key file, can't contain "Tesla"; (10) continuous REST polling (vs. telemetry push) burns the free credit in days. The literal "no reselling/sublicensing" clause in Tesla's agreement is the one term that needs primary-source confirmation (tesla.com blocked automated fetch) before going beyond a personal, single-owner build.

## car-screen

The "/screen" idea (dashboard URL on the car screen, doubling as QR-pairing + live dashboard while parked) is viable but narrow.
